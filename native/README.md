# mazes-ASK // iPhone and iPad app

The maze lab in [`../web/`](../web/) as a private iPhone and iPad app, packaged by [Capacitor](https://capacitorjs.com/). The app runs the same page, engine and design-system files from its own bundle, with no network. It adds three things the web page does not have:

- a **saved maze**, kept until you save another;
- **recovery** of the last complete maze when the app opens again;
- **share PNG**, which hands the exported image to the system share sheet, with Save Image, Save to Files and the rest.

This is a prototype for use on ASK's own devices. It is not in the App Store or TestFlight.

## What is here

| File or folder | What it holds |
|---|---|
| `package.json`, `package-lock.json` | Capacitor and its plugins, at exact versions |
| `capacitor.config.json` | the app id, name and bundle folder |
| `scripts/bundle-web.mjs` | builds `www/`, the app's copy of `../web/` |
| `ios/` | the Xcode project, generated by Capacitor and then given its icon, launch screen, bundle id and a view controller for iPad windows |
| `www/` | generated by `npm run bundle`; not in Git |

The page's native behavior lives in `../web/app/maze-native.js` and `../web/app/maze-native.css`. On the web, `maze-native.js` returns at once and the CSS is never loaded.

## The bundle

`npm run bundle` copies every file of `../web/` the app uses at run time into `www/`, byte for byte. It leaves out the checks, the READMEs, the hosting files and the link-preview card. It adds four files:

- Capacitor's core runtime, `native/capacitor.js`;
- its license;
- this repository's `LICENSE` and `NOTICE`.

`www/bundle.json` records each file's source, size and SHA-256, and the Git commit it was built from. The step stops if any copy differs from its source. There is no second copy of the maze to keep in step: change `../web/`, then bundle again.

## Build and run

You need a Mac with Xcode 26 or later and Node 22 or later. A physical device needs an Apple Account added in Xcode (Settings → Accounts). A free Personal Team is enough; its provisioning lasts seven days, after which you build and install again. The device needs Developer Mode turned on, and must trust this Mac.

```bash
cd native
npm ci
npm run sync
npm run open
```

`npm run sync` bundles the web folder and copies it into the Xcode project. `npm run open` opens the project in Xcode. There, choose the `App` target, then Signing & Capabilities, and pick your team. The bundle id is `studio.a-s-k.mazes`; if your team cannot register it, change it there. Then choose a device or simulator and Run.

After changing anything in `../web/`, run `npm run sync` again before building.

## Saved maze and recovery

A saved maze is a JSON record (`format: "mazes-ASK/saved-maze"`, `version: 1`) written by `MazeEngine.toRecord`. It holds:

| Part | Contents |
|---|---|
| **recipe** | the seed, color seed, algorithm, grid, density and frame shape the maze was made for. This is provenance: replaying it can differ in colors. |
| **geometry** | the grid's kind, composition, columns, rows and cell count |
| **graph** | the canonical carved links, the order each cell was reached, and the step count |
| **appearance** | the actual colors, after any `new colors`; the frame; and whether ends, solution and label are shown |
| **check** | a check of the record against damage |

`MazeEngine.readRecord` rebuilds the maze from its graph, not its seed, so a later change to an algorithm cannot change a saved maze. It refuses a record it cannot rebuild exactly, and says why. A refused saved maze stays as it is until you save again and confirm the replacement. A recovery file that is refused, or cannot be read at all, is moved aside to `recovery-refused.json` before a new maze is kept. Only the latest is kept there: a later one takes its place. If it cannot be moved aside, the app says so. A damaged file is then written over, but one that cannot be read at all is kept as it is, and new mazes are not kept for next time until it can be read or moved aside.

The files are in the app's Library folder, under `mazes-ASK/`:

| File | When it is written | When it changes |
|---|---|---|
| `saved-maze.json` | `save this maze` | only when you save again, after confirming the replacement |
| `recovery.json` | a maze completes, its look changes, or the app goes to the background | each time a complete maze or its look changes, unless a copy of it cannot be read (see below) |
| `recovery-refused.json` | a recovery file that is refused or cannot be read, or a last maze that was never reopened, moved here before a new maze is kept | replaced, unread, by the next one moved here |
| `building.json` | a maze being built becomes the current maze: a new maze, or undo back to an unfinished one | removed while the current maze is complete, including when its checkpoint cannot be kept |

Each file is written to a temporary copy, `<file>.tmp`, which is then renamed over the old file. The rename removes the old file before it moves the copy in, a write can stop part-way, and the app can stop between the write and the rename. So the copy, when it is good, is never older than the file: it is the same, or it is the newer record. The app keeps to these rules:

- A read takes the copy if it is good and differs from the file, and otherwise the file if it is good. Taking the copy writes it back over the file, reading it back to check, before anything else can write.
- A copy that exists but cannot be read at all, the file or its temporary copy, is never written over, because its content is unknown. A write replaces both copies, so while such a copy remains, writes to that file are refused, even when the other copy is good. Recovery first moves an unreadable file aside, as above. The app still opens a good copy if there is one; when that is the file and the unreadable copy may be newer, it says it reopened the last maze that could be read.
- If a good copy cannot be made the file, writes to that file are refused in the same way.
- A refusal lasts only while its cause does: every read and every write reads both copies again first. When saving over the saved maze is refused, the save button reads it again first: if the cause has passed, it asks as usual about what is there now; if not, it says why and writes nothing. **open saved maze** also reads it again.
- A last maze that could not be read when the app started is never written over once it can be read: it was never reopened, so the next write moves it aside to `recovery-refused.json` first, and the app says so. If it cannot be moved, the write is refused.
- The app says which copy could not be read or written back, and what follows, in notes under **saved maze**: one for the saved maze, and one while mazes are not kept for next time. The start and each refused write also say it in the status line. The other files, sharing and the maze itself work as usual. If a copy never becomes readable, the refusal stays: the app keeps working, but that file is not written again.
- A complete maze that could not be kept is reported then, not at the next start as a maze being built.
- A copy that can be read but is cut short or refused is damaged, not unknown, and may be written over. Nothing counts as missing unless the file and its copy both are; a damaged copy with no good copy beside it is reported as damaged.
- The note of a maze being built holds no maze, so a copy of it that cannot be read may be written over or removed. When the start cannot read the note at all, it says a build may not have been resumed.

The checks for this stop the app at every step of a save, in two ways: before the step, and part-way through it. They then relaunch and stop it again at every step of the next save or of the write-back, for the saved maze and for recovery. They also confirm what each stop left on disk: a stop before a step changes nothing, a write stopped part-way keeps half its text, and a rename stopped part-way has removed the old file only. Other checks, for the saved maze and for recovery, make one copy unreadable: the file alone, the temporary copy alone, or the temporary copy beside a readable file, and for recovery with moving the file aside failing too. They confirm that nothing writes over it, that the app's status and notes say so, and that the record comes back when reads work again, in the same session or at the next start. They read the text of the status line and notes, not how much of it fits on screen. These checks model the app being ended between file operations, a write cut short, and reads that fail. These are browser checks against a stand-in for the app's storage; the harness is not included in this repository. They do not cover the storage itself losing data it had already written.

**Interruption.** Going to the background and coming back keeps everything in memory, including a maze still building. If the app is closed, or the system ends it, the next launch reopens the last complete maze with its look. A maze that was still building is not resumed: the app says so, and shows the last complete maze, or a new maze when there is none. If the note of a maze being built is damaged, the app still reopens the last maze, and says that a maze being built may not have been resumed.

**A slow start.** If the app's files have not answered after one second, the page shows with a new maze, and the maze controls work on it. Saving, opening the saved maze and sharing wait for the files, and say so. When the last maze then arrives, it opens over the page's maze, with undo. If you have made a maze or changed its colors by then, yours stays, and undo reopens the last one, for 8 seconds. Nothing is written before the files answer, so if the app is closed during a slow start, a maze made in that time is not kept, and is not reported as unfinished.

## Checks

From `../web/`:

```bash
node checks/saved-maze.cjs app/maze-engine.js
```

This builds every algorithm on every grid it offers, at five frame shapes, three densities and three seeds. It saves each maze, reads it back and requires the reopened maze to equal the original: the same hash, visit order and drawing calls. It then requires thirteen kinds of damaged record, plus an incomplete maze, to be refused, each for its own reason. An optional second argument sets the number of seeds, a whole number, 1 or more. `checks/engine-sweep.cjs` is unchanged and still passes.

## Notes on the project

- **The app id.** Capacitor's `cap add` accepts only Java-style ids, without hyphens. The project was generated with a placeholder, and the Xcode bundle id was then set to `studio.a-s-k.mazes`. Running `cap add ios` again needs the same step.
- **Launch.** The web view can draw its first frame before it knows the safe areas, and the first maze waits for the app's files. So `maze-native.js` runs in the page's head and keeps the page's content hidden over the page field until both are ready, for one second at most. At that second the page makes its own first maze if the files have not answered (see **A slow start**). Before the page loads, the launch screen and the web view show the system background, white or black.
- **iPad windows.** In a resizable window, iPadOS draws its window controls over the top-leading corner of the app, outside the safe area. `ios/App/App/MazeBridgeViewController.swift` adds the height they need to the top of the safe area while they are there, so the page's header starts below them. `SceneDelegate.swift` uses it in place of Capacitor's own view controller; running `cap add ios` again needs the same step. A full-size iPad and iPhone are unchanged.
- **Fullscreen.** On iPhone the app offers **full window** only, as Safari on iPhone does. The app's web view would offer fullscreen there, but it runs under the Dynamic Island. On iPad, `fullscreen` appears as it does in Safari, and while it is on, the system names the app's internal address, `capacitor://localhost`. **full window** works on every device.
- **Links** to the web, such as the source on GitHub, open in the device's default browser, never inside the app.
- **Not built:** Android, the App Store, TestFlight, or any account or cloud sync.
